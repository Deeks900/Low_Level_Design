I separated responsibilities across LogMessage, Formatter, Appender and Logger. LogMessage represents the data, Formatter handles formatting, Appender handles the destination, and Logger orchestrates the logging workflow. This prevents changes in one responsibility from affecting unrelated components.

I used abstractions for Formatter and Appender so new formatting strategies or output destinations can be added through new implementations rather than modifying Logger. This follows the Open/Closed Principle.

This is called Producer–Consumer

This is a very important concurrency pattern.

You don't need to memorize the name yet. Just visualize it.

PRODUCERS                         CONSUMER


Thread 1 ──┐
Thread 2 ──┤
Thread 3 ──┼──► [ LOG QUEUE ] ──► Worker Thread
Thread 4 ──┤
Thread 5 ──┘

The queue is the meeting point between them.

Why do we need a queue?

Suppose the application is producing logs faster than the disk can write them.

For example:

Application produces:


1000 logs/sec

but disk can process:

200 logs/sec

We don't want the application threads to wait for the disk.

Instead:

1000 logs/sec
      ↓
 ┌───────────────┐
 │ LOG QUEUE     │
 │               │
 │  log1         │
 │  log2         │
 │  log3         │
 │  ...          │
 └───────────────┘
      ↓
  200 logs/sec
      ↓
     Disk

The queue acts as a buffer.

                Shared Queue
                     │
                     ↓
                  mutex
                     │
              protects queue

Instead, we want the worker to basically say:

"Wake me up when there's a log message."

And THAT is what we'll learn next:

condition_variable

It's essentially a mechanism that lets a thread sleep until another thread tells it that something interesting has happened.
